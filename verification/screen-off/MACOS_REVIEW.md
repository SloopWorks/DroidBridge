# macOS expert review — screen controls, 0.1.4 build 9

Outcome: approved within the verification scope below; no concrete release blocker found. This was a read-only production-source review. No packaged input was changed.

Reviewed `PhoneDisplayControls.swift`, `PhoneDisplayPower.swift`, Launcher/AppDelegate integration, subprocess execution, and fallback stream/startup descriptor ownership.

- Phone control is separate from session teardown. UI requests persist device-specific intent, and bounded asynchronous work selects the focused native session, owning wrapper device, or selected launcher device. Automatic maintenance targets running sessions; explicit menu requests also work without a session. An ON request remains queued after a transport failure. Timers and state callbacks invoke the same coordinator.
- App termination cancels and awaits phone-control work alongside existing owned tasks. Session close and application quit do not silently change persistent phone-screen intent. Core actuation uses a per-device, close-on-exec mutex, checks current shared intent around asynchronous boundaries, compensates superseded effects under the same mutex, and verifies INTERNAL display 0 independently of virtual displays.
- Fallback stream ports use distinct per-port locks plus exclusive bind preflight. The port descriptor is intentionally passed as supervisor stdin, so its open-file description remains owned through child cleanup even if the GUI dies. Releasing the GUI reference closes it without prematurely unlocking the inherited reference. Stop retains the lease until the exact supervised process has been reaped.
- The per-device startup descriptor is a separate close-on-exec lease. It is not the inherited stdin lease and stays alive through the application's startup confirmation. This serializes display/task initialization without serializing the lifetime of otherwise concurrent app windows.
