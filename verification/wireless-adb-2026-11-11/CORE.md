# Wireless ADB Core evidence

- [AOSP wireless ADB architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md) documents Android's QR payload, the separate pairing and connection services, and the device GUID. DroidBridge generates a fresh QR-compatible service name and a 128-bit secret per attempt, scoped to the phone's built-in scanner. The secret goes to the owned `adb pair` client through stdin and is absent from app logs, process arguments and profile storage.
- The bundled ADB 37.0.0 source at `.build/adb-runtime-work/android-tools-37.0.0/vendor/adb/client/adb_wifi.cpp` accepts a numeric pairing endpoint and returns `Successfully paired to … [guid=…]`. Its paired connection auto-discovery is omitted. `CompanionWirelessBonjour.swift` browses the native local Bonjour service with a deadline and cancellation; it never changes the shared ADB daemon's discovery settings. [Apple TN3179](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) describes the Local Network authorization this requires.
- The first QR connection requires the GUID returned by ADB pairing and the numeric host that received the QR-authenticated pairing. The ADB device list must contain exactly one ready matching serial and transport ID before DroidBridge reads its Android ID. Stock API 35 can hide `persist.adb.wifi.guid` from shell, so a blank GUID does not confirm or reject the peer; a readable mismatch rejects it. The raw Android ID is not logged or persisted. Only a domain-separated digest supports future continuity checks across address changes. Android may represent the 64-bit ID without leading zeroes ([AOSP SettingsProvider](https://android.googlesource.com/platform/frameworks/base/+/3023aab546391b67d049460f84a3ae52b81616a4/packages/SettingsProvider/src/com/android/providers/settings/SettingsProvider.java)).
- The pinned ADB host TLS client in `vendor/adb/transport.cpp` allows any server certificate. The above checks help with ordinary stale/changed endpoints and are not mutual peer authentication against an adversarial LAN. Companion TLS pairing stays separate. A mismatch closes only a transport the current ADB client reports opening, after rechecking its exact transport ID; a previously attached transport is left alone.

Focused checks: `swift test --filter 'CompanionWirelessADBTests|CompanionWirelessReconnectTests'`; output in `swift-core-continuity-final.log`. The earlier process test revealed that Foundation `waitUntilExit` could block with in-memory pipes on a cooperative worker; the final runner uses a bounded cancellation and termination callback. Tests with fake ADB executables exercise stdin, redaction, confirmed results, exact transport IDs, and cleanup; emulator and packaged app verification are recorded separately.

Native DNS-SD smoke test (`core-bonjour-smoke.log`): registered two ephemeral loopback advertisements using Apple's `dns-sd -P`. The shipping Core located the exact QR request, supplied its secret only through stdin to a fixture ADB, found the same-host connection advertisement, verified the fake ready transport with the shell GUID hidden, and canceled an unmatched browse within its bound. This validates the Mac resolver and command boundary; the fixture does not claim Android pairing or camera acceptance. After `swift test`, compile the driver with `swiftc -parse-as-library -I .build/debug/Modules verification/wireless-adb-2026-11-11/core-bonjour-smoke.swift .build/debug/DroidBridgeCore.build/*.swift.o -o "$qa/probe"`, then run `"$qa/probe" "$qa"` with `$qa` a disposable mode-700 directory.
