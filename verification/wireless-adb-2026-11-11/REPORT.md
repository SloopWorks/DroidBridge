# Wireless ADB setup and recovery — November 11, 2026

Implemented in local review build 25. See the [implementation plan](PLAN.md), [artifact fingerprint](artifact.json), and [Core evidence](CORE.md). Three agents handled Mac pairing/discovery, saved reconnect/USB, and Android companion guidance. The integration work wired the Mac setup panel and main-app polling, packaged the app, and exercised the dedicated emulator.

## Product behavior

- **Devices → Connect over Wi-Fi** shows a fresh QR on first setup. On Android, use **Developer options → Wireless debugging → Pair device with QR code**. Android owns debugging and network approval; the Mac displays the invitation without accessing its camera.
- **Use Connected USB Phone** uses the selected authorized USB transport to read one WLAN address and a local continuity fingerprint. It connects to the matching Android TLS service only if the wireless fingerprint agrees. QR is available if the phone needs fresh trust. Companion setup explains the routes and opens Developer options through a public intent; companion sharing has separate approval.
- **Manual Setup** hides both address fields and the code until requested. After code pairing, the Mac tries to discover the connection automatically; the second address is needed only when discovery cannot complete.
- The main Mac app remembers only verified phones and looks for their current address while open. **Reconnect Saved Phone** retries explicitly; **Forget Saved Phone** stops automatic reconnect, with Android trust managed separately. A moved or stale numeric alias does not authorize a new app session on the wrong device. An existing window on a changed alias may need reopening on the recovered connection.

The stock Android TLS debugging protocol authorizes the Mac; the stored Android fingerprint checks ordinary device continuity and does not establish mutual certificate pinning. Discovery is scoped to the one-time QR, a selected USB phone, or previously verified saved phones. No new cloud service or shared ADB server changes are needed.

The packaged runtime driver was `python3 scripts/verify-wireless-adb.py --app <external-build-25.app> --probe <private-swift-probe> --output <evidence-dir>`. The QR scenario uses `--direct-camera`; the passing rotation scenario uses `--android-code --overlap-advertisements`. The probe links the shipping UI, Core and Streaming sources. Build 25 was produced by `scripts/package.sh` with ad hoc signing, the locally signed companion release APK, and `.build/adb-runtime/adb`. The test device's first-use network approval was performed through Android Settings.

The emulator is behind NAT. The verifier used temporary loopback forwards and DNS-SD proxy registrations to reach the real guest pairing and TLS servers. That verifies Android Settings, PAKE, transport continuity, and video without claiming physical Wi-Fi reachability, macOS first-use permission behavior, or a physical USB test. Physical Pixel testing remains with the owner.
